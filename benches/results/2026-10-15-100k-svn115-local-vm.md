# Benchmark: OpenSVN engine vs svn CLI

- svn CLI: svn, version 1.15.0 (r1937767) (1.15.0)
- server: Apache/2.4.69 (Unix) SVN/1.15.0, HTTP on 127.0.0.1
- dataset: 100000 text files + 4 x 64 MiB binaries, 452 MiB in r1
- machine: Intel(R) Xeon(R) Processor, 4 CPUs, 15.7 GiB RAM, Linux 6.18.44-fc-v114
- filesystem of the working copies: ext4 on /dev/vda (rw,relatime,discard,no_prefetch_block_bitmaps,resv_strict,resuid=65534,resgid=65534); NOT journaled (no jbd2 journal for this device)
- build: release
- repetitions: 3 (median shown, min in brackets; every repetition below)

## Notes

- **Acceptance** (#121): the engine is not slower than svn 1.15.0 in any operation (median of 3),
  and the repeat status of 100,000 files takes 0.29 s (< 3 s). Against the 2026-10-14 run (svn
  1.14.3, before the batched sync and the one-transaction status walk) the engine went from 947 s
  to 45 s for the checkout, 83 s to 8.4 s for the update and 14.7 s to 0.29 s for the repeat status.
- **Checkout varies a lot between repetitions** for both clients (svn 35 to 63 s, engine 41 to
  70 s) on this VM's virtual disk, and the engine was slower than svn in two of the three
  repetitions taken one by one (41.4 vs 35.3 s, 70.5 vs 49.4 s) while faster in the median.
  Repeat on quieter hardware before reading a ratio off one pair.
- **Where the checkout's time goes** (`strace -f -c` through `OPENSVN_BENCH_WRAP`, 20,000 files,
  counts per file): the engine makes 3 `openat`, 4 `pwrite64`, 2 `copy_file_range`, 2 `rename`
  and 29 `fcntl` (SQLite locks) per file, svn 4 `openat`, 47 `pwrite64` (its SQLite journal), 22
  `fcntl`. The engine's measurable waste is about 11 failing `stat` calls per file: 7 are SQLite
  probing for a hot `wc.db-wal` at every connection or read transaction it opens (the database
  runs in rollback-journal mode, so the file never exists), 2 are obstruction checks of the file
  and of its parent directory before the directory exists. Neither is the bottleneck today (the
  engine wins the median), but both scale with the file count: reusing one connection per
  operation and checking a directory once before its children would remove them.
- **Filesystem**: the VM's ext4 runs without a journal (`/proc/fs/jbd2` has no entry for
  `/dev/vda`), so every `fsync`/`syncfs` is cheaper than on a journaled ext4 (data=ordered), which
  favours whichever client syncs more. In the 20,000-file trace svn issued no `fsync` at all;
  the engine issued 78 `syncfs` (one per batch, `BATCHED_SYNC`) and 412 `fsync`.
  On a journaled disk those cost more, and only the engine pays them.
- **macOS and Windows** still sync every file (`BATCHED_SYNC` is Linux only,
  `crates/svn-wc/src/durable.rs`); see "Sync per file on macOS and Windows" in
  `benches/README.md` for the measurements still needed there. This run says nothing about them.
